# 智能实验模块架构

## 数据流

用户选择运行 / 粘贴日志 / 示例 → 主进程收集有限日志和结构化证据 → 脱敏与规则诊断 → 可选模型选择工具 → 工具及参数、证据引用校验 → 只读检查 → 结果再次交给模型（有限循环）→ 最终 JSON 结论校验 → 本地报告 → 用户审查修复 → 新运行队列 → 调度器 → 重新读取远程退出码核验结束状态。

自然语言计划：用户指定服务器、代码目录与环境 → 模型解析需求 → JSON/schema 校验 → 单 Python 脚本命令检查 → 可编辑草稿 → 用户确认保存 → 原有实验任务页明确加入队列。

## 模块

- `shared/intelligence.ts`：IPC 契约与报告数据。
- `shared/diagnosis-engine.ts`：脱敏、日志边界、证据化规则、受限 batch size 修复。
- `main/diagnostic-agent.ts`：模型检查循环、4 轮 / 4 项预算、参数与证据校验、重复检查处理、取消与过程记录。
- `main/diagnostic-tools.ts`：固定只读工具目录，路径 / 依赖文件 / 包范围校验，真实运行及受信任连接检查。
- `main/model-provider.ts`：兼容 Chat Completions 传输、45 秒超时与 AbortSignal 取消、JSON 解析、禁止重定向。
- `main/repair-tracker.ts`：每 30 秒观察、调度事件唤醒、单运行核验互斥、缺证据退避、暂停取消与持久化状态恢复。
- `main/intelligence-service.ts`：证据采集、持久化、模型设置加密、计划校验、重试与验证。
- `renderer/src/components/IntelligencePage.tsx`：证据工作区、计划审查、模型设置。
- 原有 `experiment-scheduler.ts`：目录/环境/GPU 启动前检查、运行日志、退出码和任务状态。

## 关键边界

模型通过 JSON 指定受支持的检查名称及参数，主进程根据已有运行配置和日志核对范围，再用固定 SSH 命令模板读取结果。模型不能提供任意 Shell 命令。自动修复由确定性模板生成，限于失败运行的显式 batch size 减半；来自模型的猜测不能开启该动作。重试需要确认，检查旧运行及命令是否变化，并防重复创建。普通 GPU 当前快照不能用来证明失败发生时的资源状态。

日志最多保留 240 行 / 64 KiB，行号相对于报告片段。规则匹配的“明确错误信号”只描述日志错误类别，不意味着已确定所有根因。模型引用 ID 校验只能保证引用存在，不能保证推理一定正确；建议需继续通过检查或新的实际运行验证。

## 多轮协议与持久化

模型返回 inspect（最多两个 toolCalls）或 final（summary / findings）。每个选择和结论必须引用已向模型提供的证据。检查返回 success / failed / unavailable，成为 check-N 证据；失败与不可用不会被转换成目标不存在。第四轮或检查额度耗尽时强制 final；不遵守协议则保存规则报告与部分记录。

requestId 关联 IPC 进度与取消。取消模型 HTTP 请求、关闭本次工具 SSH 连接，并在后续调用前检查信号；GPU / Conda 现有服务不接受取消信号，因此这些已开始的读取等待返回或底层超时，不继续新的检查。报告保存使用串行队列，避免并发诊断互相覆盖。历史 schema 兼容 0.1.0 报告。

日志、依赖文件与工具结果被提示为不可信证据，不能作为改变任务的指令。过程记录仅展示工具选择和简短检查目的，不保存模型的隐含推理过程。模型的最终结论与规则结论并列，来自模型的推测不能启用可执行修复。

## 修复闭环

retry 在原运行命令和来源不变、用户明确确认后创建新运行，并持久化 closure.enabled=true。调度器状态变化唤醒 RepairTracker，独立 30 秒定时器补偿遗漏事件。queued / preparing / running 只观察本地记录；completed / failed 重新读取远程 exit-code。

状态：waiting → running → verifying → passed / failed / attention。退出码 0 才能 passed；非零退出码生成或复用该新运行的诊断，保存 nextDiagnosisId。模型是否启用沿用原诊断选择，具体服务使用当前有效设置；诊断失败或取消不会被解释成修复成功。失败阶段不创建新运行，新的 repair 再次经过审查确认。

单份报告的手动 / 自动验收共享同一 Promise，避免重复连接和重复生成诊断。证据未知会退避 30 秒、120 秒，最多三次自动核验；取消 / 暂停 / 记录丢失则直接 attention，等待用户处理。暂停跟踪取消正在进行的验收 / 模型诊断，并阻止迟到结果覆盖暂停状态。

closure 包含状态、启用标记、核验时间、退出码、尝试次数及新诊断 ID，通过报告写队列原子持久化。启动时恢复启用的跟踪，并核对运行 notes 的诊断来源标记，补回“运行已创建而报告未保存”的关联。历史上限优先保留启用的跟踪报告。

IPC history-changed 推送触发界面刷新，即使用户离开智能实验页，后台服务仍继续观察。正常退出仅证明进程结束，不包含训练质量判定。

## 验收

类型检查、生产构建、规则/传输/生命周期回归测试、实际 Electron preload/IPC、进度 / 停止按钮、工具结果定位和截图检查。模型 HTTP 测试使用本机模拟响应；SSH 生命周期测试使用模拟连接。本版未在真实训练服务器上执行或验证修复。

## 0.4 任务上下文与离线演示

App 传递 IntelligenceRequest（任务、运行、报告 ID），任务栏使用 reportForRun 匹配同一任务的准确运行；修复运行自己的新诊断优先于原诊断的修复关联。导航不自动采集或运行。生成计划在保存时清除草稿 ID，以新任务保存。

DemoWorkflow 会话位于 App 内存覆盖层，仅合并进任务栏与智能实验页的显示列表，不加入后台服务器/调度列表。demo-workflow.ts 不依赖 IPC、网络或文件系统，诊断复用 diagnosis-engine。模拟诊断、修复、运行与验收通过独立回调推进；模型开关对模拟任务禁用，模拟报告不调用导出/核验/跟踪接口。离开或重置时移除会话 ID 对应的 UI 选择。

运行返回通过 TaskPool request 的 runId 展开与高亮；已删除的关联返回按钮禁用。历史加载异步时保留报告导航请求，读取完成后才消费。
